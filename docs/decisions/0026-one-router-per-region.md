# 0026 — One GraphHopper per region, addressed by port; a route that cannot place itself refuses

Status: **accepted**, M9, 2026-09-16.

## Context

Five regions are built into PostGIS. Until M9 two had a routing graph, and every config in
`deploy/graphhopper/` bound port 8989, so only one could run at a time. `core/routing/
graphhopper.py` reads one `LONGRUN_GRAPHHOPPER_URL` with one default, and every call site
resolves through it with no notion of *where* the route is.

The gap was already documented from the other end. `tests/contract/test_graphhopper.py` skips
rather than fails when the graph does not cover the Bay Area, with the comment: *"one port
serves one graph, and once a second region exists — which is scope 11's plan and M3's exit
criterion — the server on 8989 is as likely to be Phoenix as the Bay Area."*

One graph per process is GraphHopper's constraint, not a preference: `datareader.file` and
`graph.location` are single-valued, and `load()` refuses a graph whose stored `profiles`
string differs from the configured one.

## Decision

### A committed registry, `deploy/regions/routers.yaml`, mapping region → port and heap

**A port is deployment topology, not part of what a region is.** `RegionSpec` is committed so
that two plans of the same region are comparable whoever ran them; a spec carrying a port would
make the machine part of the comparison. So the registry is a separate file, read by
`regions/routers.py` — never by `core/`, which may not read a deploy file.

**Ports sit two apart** because GraphHopper's admin connector is always `port + 1`. A one-step
gap collides the next region's HTTP port with the previous region's admin port, and the
collision surfaces at bind time as a message naming the wrong region.

**Heap is per region.** The default was `-Xmx6g`; five of those reserve 30 GB. The Bay Area is
361 MB of graph and gets 6g, the Ozarks is 9 MB and gets 1g.

**The Bay Area keeps 8989**, which is `DEFAULT_URL` and the value in `.env.example`, so every
setup predating this file works untouched.

### Resolution order, most specific first

1. `--router` / an explicit URL
2. `LONGRUN_GRAPHHOPPER_URL_<REGION>`
3. the registry
4. `LONGRUN_GRAPHHOPPER_URL`
5. `http://localhost:8989`

Rungs 4 and 5 are the compatibility guarantee: a machine with one region and one env var never
reaches the registry at all.

### A route that cannot place itself falls back and says so — it never guesses

**A route drawn on the wrong region's graph is the worst output this project can produce,
because it is plausible.** It has real streets, a real distance, a real elevation profile and a
real cue sheet, all belonging to a different city. Every check in §7.9 passes. Nothing
downstream can detect it.

So `region_for` requires *every* waypoint in one region, and reports ambiguity rather than
resolving it:

- waypoints in two different regions → names both, "no single graph covers the route"
- waypoints in no built region → says so
- waypoints inside two overlapping region polygons → names them, asks for `--region`

In each case `resolve` falls back to the single-region default **with the reason in the line it
prints**, rather than refusing outright. Refusing would break every one-region setup, which is
the configuration this project shipped with for eight milestones. Falling back is safe because
the failure that follows is honest: a Bay-Area-to-Boston request produces GraphHopper's own
out-of-bounds error, not a line.

### Configs are generated from the spec and committed

`config-phoenix-lts.yml` was a hand-copy of `config-bayarea-lts.yml` with two lines changed. It
still carried the Bay Area's extract command and bbox in its header — wrong from the moment it
was written, and invisible because nobody re-reads a config they did not change.

Generated by `longrun region-config`, checked by a unit test that regenerates all five and
fails on a diff. So a hand-edit is reverted by CI rather than silently kept.

**Committed rather than rendered at run time**, because `GraphHopper.load()` compares the
config's `profiles` against the string stored in a built graph and refuses a mismatch: a config
that regenerated differently — a reflowed block, a changed comment inside `profiles` — would
take every built graph offline at once. A committed artifact with a regeneration test makes
that a reviewable diff instead of an outage.

## Consequences

- Five JVMs can run at once, started on demand. Verified: all five served simultaneously, each
  reporting `lts` in its encoded values, and `longrun plan` drew a line in each.
- **`import-lts.ps1` refuses an existing graph directory.** Discovered while rebuilding: the
  import *loads* an existing graph rather than rebuilding it and exits 0, so Phoenix and the
  Bay Area "rebuilt" in 1.4 s each and kept their September 4 and 10 graphs, placeholder scores
  intact. Nothing was wrong anywhere except the answers. `-Force` replaces; without it the
  script names the graph's build date and stops.
- `run.ps1` and `import-lts.ps1` share one registry reader (`registry.ps1`), because importing
  with one config and serving with another is how GraphHopper's profiles-mismatch refusal is
  produced, and a single resolver is what prevents it.
- `SnapshotPins.region` records which graph answered, so two plans are attributable.
- Not yet done, and named rather than implied: `tools/routing.py` builds three bare routers
  from the env var with no cache, no budget and no region, and `api/app.py` constructs empty
  `SnapshotPins`, so the MCP and HTTP surfaces still resolve one router for the world. Both are
  clients of this decision rather than changes to it.
